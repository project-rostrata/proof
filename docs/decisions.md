# Decisions log

An append-only record of decisions made while building proof, beyond what `PROJECT_BRIEF.md` and `V1_PLAN.md` already fix. The newest entries are at the bottom. Don't relitigate any of these without flagging it to the human first.

## 2026-10-02 — App name: proof

Named after the proof sheet (contact sheet), which is what culling is done on. It pairs with `press`. Other candidates considered: easel (rejected as "too painterly"), mantel, tray, plate, and contact.

## 2026-10-02 — Edits render entirely in the browser (WebGL2)

Three options were weighed for where the edit pipeline runs:

1. **Kotlin renders everything.** The server renders a debounced preview from a cached working copy, and renders the export. There's one implementation, and the UI stays fully dumb. But every slider movement costs a network round-trip plus a JPEG encode, so it would never feel like Snapseed.
2. **A WebGL preview plus a Kotlin export.** This feels instant, but every tool gets written twice, in GLSL and in Kotlin, and the two drift apart. The result is that what you see isn't what gets saved.
3. **The browser renders everything.** There's one implementation, in the place where it has to be fast anyway.

The human chose option 3, with one refinement: the browser sends the finished render back to the API, and the server stores it. A photo that's mid-edit is ephemeral working state. Once it's saved, the server holds the truth, which is just generated by the browser. Consequences:
- The server never runs an edit pipeline.
- Thumbnails and exports come from the stored render.
- The "API is source of truth / dumb UI" rule from `larder` gets one narrow, recorded exception for pixels (see the next entry).

## 2026-10-02 — Narrow exception to the dumb-UI rule: the pixel pipeline

The standing rule (filtering, formatting, and derived values belong in the API) still holds for everything in proof except pixels. The WebGL pipeline lives only in `frontend/src/pipeline/` and never touches project, rating, or list state. Cull views, counts, and display strings all come from the API. See `AGENTS.md`.

## 2026-10-02 — Store the render *and* an opaque recipe

Saving an edit stores two files: the full-resolution rendered JPEG and a JSON recipe (the edit stack with its schema version). The server validates the recipe only as JSON within a size cap and never interprets it. It hands the recipe back unchanged so the browser can reopen the stack and keep editing non-destructively, like Snapseed's "View edits". The alternative, storing the render only, was rejected because it would make re-editing start over from the original, for the sake of saving a few KB per photo. Recipe schema migrations are entirely the frontend's job.

## 2026-10-02 — Files are the truth, with a Postgres index (`shelf`'s model)

Photos have an obvious natural file form, and users may want to reach them from outside the app (SMB, darktable). So originals, renders, recipes, and XMP rating sidecars are real files, and Postgres is a rebuildable index over them, with `shelf`'s reconciliation machinery reused. The alternatives were:
- **Postgres as the source of truth** (`larder`'s model), rejected because it locks cull and edit work inside the app;
- **files with no database** (`press`'s model), rejected because cull views need fast filter, sort, and count queries over hundreds of photos per project.

## 2026-10-02 — v1 input formats: JPEG and PNG only

`javax.imageio` handles both with no new dependency. EXIF reading and the EXIF re-attach on save are hand-written, needing only a small TIFF IFD parser and a byte-level APP1 segment splice. HEIC and camera RAW are deferred to v1.5. They'd most likely use apt-packaged CLI decoders run through array-args `ProcessBuilder` (`press`'s pattern), proposed as a dependency at that time.

## 2026-10-02 — Single-shot per-file uploads, not chunked

Photos are 5–20 MB each, so a client-side queue of about 3 concurrent single-file `POST`s, each streamed to disk, is enough. This is `press`'s reasoning. `shelf`'s chunked/resumable machinery is for multi-gigabyte, possibly multi-day transfers, which this app doesn't have.

## 2026-10-02 — WebGL2 spike comes first

The browser pipeline is the one genuinely novel risk in the project, in the same way the printer driver was for `press`. `V1_PLAN.md` Phase 1 is a throwaway spike that measures, on the real target devices: 24 MP texture load, interactive frame rate with a stacked pipeline, half-float support and banding, full-resolution export time, colour fidelity, and the EXIF splice. Its findings, with numbers, get recorded here before any repo code is written.

## 2026-10-02 — The edit pipeline builds on mini-gl (approved dependency)

The human asked to look for an existing library rather than reinvent the basic photo-editing shaders. The options surveyed:
- **glfx.js:** MIT, but WebGL1, last pushed in 2023, and lacking shadows/highlights and white balance.
- **WebGLImageFilter:** mostly colour-matrix effects.
- **LYGIA:** a GLSL function library under a non-standard licence (GitHub can't identify it as an OSI licence), which is unsafe to assume is GPL-compatible.
- **WASM CPU engines** (wasm-vips, Photon, OpenCV.js): megabytes in size and too slow for live sliders at 24 MP.
- **Full editor libraries** (Fabric.js, Filerobot, TUI Image Editor): large, bundle their own UI, and the wrong shape.

**mini-gl** ([xdadda/mini-gl](https://github.com/xdadda/mini-gl), MIT, two ES modules of about 30 KB, no dependencies, WebGL2, built on glfx.js) covers most of the v1 tool list: brightness, exposure, contrast, shadows/highlights, temperature/tint, vibrance, saturation, curves, clarity, vignette, perspective, crop, and rotate. It's a single-maintainer project (37 stars, last pushed December 2025), so the plan is to vendor a pinned copy, the way VanJS is vendored, and be ready to own it.

Approved on these terms: the Phase 1 spike decides between vendoring mini-gl as-is and forking it into `src/pipeline/`. No other graphics or image library is approved. Recorded in `PROJECT_BRIEF.md` §2.

## 2026-10-02 — Phase 1 spike: headless correctness findings (real-device numbers still pending)

Built in `spike/` (see `spike/README.md`). It tests mini-gl upstream at commit `28238857` (v0.1.19) as-is, with SRGB8 intermediates, against a fork that changes one thing: RGBA16F intermediates. It was run in headless Chrome 154 on SwiftShader in the dev VM, driven over CDP from Node's built-in WebSocket (no npm). **SwiftShader is a software GPU, so none of its timings are meaningful.** Only correctness carries over.

- **Orientation:** Chrome uploads EXIF-rotated JPEGs to the WebGL texture upright, and `naturalWidth`/`naturalHeight` are already rotated. The render is therefore upright, and the server should reset Orientation to 1 when it splices Exif back in. Safari is unverified.
- **Exif:** `canvas.toBlob` output carries no Exif. Splicing the original's APP1 right after SOI, with Orientation set to 1, preserves Make, Model, and DateTimeOriginal, and the result still decodes. Only the Exif APP1 is copied and never the ICC profile (APP2), because the render is sRGB. The Kotlin implementation should follow this.
- **Colour:** the GPU identity path is within 1 level of the browser's own 2D decode (0.02 mean). A JPEG 0.92 round trip adds a mean error of 0.14.
- **mini-gl's tonal filters have quality defects that precision doesn't fix.** On a 256-level gray ramp, each tool alone at a mild setting:
  - Contrast +0.15 clips 53 input levels to black, because it pivots at 0.5 in linear light.
  - Brightness +0.1 lifts black to gray 44, because it's a linear offset.
  - A mild S-curve clips 18 levels.
  - Even an *identity* curve maps input levels 0–6 to 0. The Curves LUT is 256 entries of 8 bits, applied to linear values. This breaks the identity-at-defaults rule in `AGENTS.md`.
- **Half-float intermediates help, modestly.** On the tonal stack, the largest visible step between levels falls from 9 to 5. But they expose a NaN in Highlights/Shadows: it divides by luminance, which is zero on pure black. 8-bit storage clamped the NaN away, but float keeps it, and the next spatial filter spreads it to neighbouring pixels. Every upstream shader would need auditing for NaN and out-of-range values before running it on float.

Current leaning, to confirm once real-device numbers are in: fork rather than vendor as-is. Keep mini-gl's structure and the parts that hold up (ping-pong runner, sRGB-correct texture handling, perspective warp, blurs, bilateral denoise, vignette, matrix transform, cubic spline). Run on half-float intermediates. Rewrite the tonal tools in a perceptual space, with a float LUT and safe handling of black.

## 2026-10-02 — Phase 1 spike: real-device results (Firefox 156, Linux desktop)

The human ran `spike/` on Firefox 156 on their Linux desktop (16 cores; Firefox masks the GPU name) with a real Olympus E-PL7 JPEG (4608×3456, 15.9 MP). **Every correctness finding from the headless run repeated exactly**: orientation upright (now confirmed in Firefox as well as Chrome), the Exif splice round-trips, the same Curves and contrast clipping, and the same Highlights/Shadows NaN in half-float. With a real GPU, the identity render is *exactly* equal to the browser's 2D decode.

Performance with the 6-tool stack (7 GPU passes):
- **Interactive preview (1600×1200):** 8 ms per frame with 8-bit intermediates, 13 ms with half-float. Both are comfortably above 60 fps, so the extra precision costs nothing that matters where it's used.
- **Full resolution (15.9 MP):** 46 ms per frame in 8-bit and 95 ms in half-float. That isn't interactive, but it doesn't need to be: editing runs on the preview-sized copy, and full resolution only renders on save.
- **Full-resolution save:** about 630 ms end to end (render, `readPixels`, `putImageData`, `toBlob` JPEG at 0.92, Exif splice), with no context loss.
- **Banding:** on the tonal stack, half-float halves the biggest visible step between levels (11 to 5) and keeps more distinct levels (188 against 161).

The human's verdict on feel: "pretty good". The sliders felt a little sensitive, since nobody uses the full range outside of deliberate art effects. That points at mini-gl's mapping from parameter to strength, which the tonal rewrite owns anyway. Snapseed-style ±100 sliders with a gentler response near zero belong in each op's parameter schema.

Still untested: Safari and iPad. That only matters if they're target devices (brief §5).

**Proposed, awaiting the human's sign-off: fork mini-gl into `frontend/src/pipeline/`** rather than vendoring it as-is:
- **Keep:** the ping-pong runner, sRGB-correct texture handling, and the perspective, blur, bilateral denoise, vignette, matrix and spline code.
- **Switch:** intermediates to half-float.
- **Rewrite:** brightness, contrast, curves and highlights/shadows. They should work in a perceptual space, use a float LUT, handle black without NaN, and use softer slider response curves.
- **Edit on a preview-sized source** (the server's 2048 px preview), and render the original at full resolution only on save.

## 2026-10-02 — Phase 1 spike: phone results (Firefox 157, Android, Pixel 7a)

Tested with a real Pixel 7a JPEG (3024×4032, 12.2 MP). Firefox masks the GPU name. Every correctness result repeated on mobile: orientation upright, an exact identity against the 2D decode, the Exif splice OK, and the same tonal defects and half-float NaN.

- **Preview (1200×1600):** median 13 ms per frame in 8-bit and 20 ms in half-float. The half-float p95 is 34 ms, so there are occasional dropped frames, but it's usable. If phones become a primary target, a smaller preview on phones is the obvious lever.
- **Full resolution:** 33 ms (8-bit) and 38 ms (half-float) per frame.
- **Full-resolution save:** 489 ms (8-bit) and 527 ms (half-float). No context loss.
- **Banding (tonal stack):** the biggest step goes from 7 to 6, and distinct levels from 173 to 193.

**GPUs don't produce bit-identical output.** The identity Curves error is 6 levels on the desktop and 7 on the phone. The same recipe re-rendered on a different device can therefore differ by a level or two. That's fine, because the stored render is the truth (brief §4). But `AGENTS.md`'s "a saved recipe must always reopen to the same pixels" has to mean *visually the same, within a tested tolerance*, and the pipeline tests must compare with a tolerance rather than exact equality.

## 2026-10-02 — mini-gl provenance audit: what the fork may and may not carry over

proof is GPL-3.0-or-later. mini-gl itself is MIT (© 2025 xdadda) and is derived from glfx.js, also MIT (© 2011 Evan Wallace). MIT code can be included in a GPL-3 work as long as both copyright and permission notices are kept. **But several mini-gl filters cite outside sources whose licences are *not* MIT**, and mini-gl's MIT licence can't relicense code its author didn't own. Going through each file:

| Upstream piece | Cited origin | Verdict |
|---|---|---|
| `minigl.js` core (Shader, Texture, ping-pong runner) | glfx.js (MIT) | **Keep.** Retain both MIT notices. |
| `filters/cubicspline.js` | glfx.js (MIT) | **Keep.** |
| `filters/filterPerspective.js` | glfx.js (MIT), with the math noted as "from javax.media.jai.PerspectiveTransform" | **Keep.** The standard square-to-quad homography is a formula, not copyrightable expression. |
| `filters/filterMatrix.js` | mini-gl's own | **Keep.** |
| `filters/filterCurves.js` | glfx.js (MIT) | Licence fine, but **rewrite** (an 8-bit linear LUT breaks identity). |
| `filterAdjustments` (brightness, contrast, saturation, exposure, temperature, tint, vibrance, clarity, vignette) | Comments say "from" **Pintura** (a proprietary commercial editor), a tsev.dev blog post (no stated licence), and PixiJS (MIT) | **Don't carry over.** The colour matrices themselves are textbook math, but the file explicitly says it was taken partly from proprietary code. Rewrite from first principles. The tonal parts needed rewriting anyway. |
| `filterHighlightsShadows` | A Stack Overflow answer from 2014, so **CC BY-SA 3.0**, which isn't compatible with GPLv3 (only CC BY-SA 4.0 is one-way compatible) | **Don't carry over.** It's being replaced anyway, with a local, mask-based version. |
| `filterNoise` (bilateral), `filterBloom`, `filterBlurGaussian`, `filterBlurBokeh` | **Shadertoy** shaders. Shadertoy's default licence is CC BY-NC-SA 3.0 unless the author states otherwise, and those pages couldn't be fetched to check. | **Don't carry over.** "NonCommercial" is an extra restriction the GPL forbids. Gaussian and bilateral filters are textbook algorithms, so we write our own. Bloom and bokeh aren't v1 tools. |
| `filters/filterInsta.js`, `filters/filterBlend.js` | mini-gl | **Drop.** Not needed. |

This narrows the "keep" list in the previous fork proposal: **blurs, bilateral denoise, and vignette are no longer kept.** The fork carries over the GL core and runner, the spline, the perspective warp, and the matrix transform. Every pixel filter is written fresh. darktable (GPL-3.0-or-later, the same licence as proof) can be used as a reference, or even directly, for the harder algorithms such as local contrast and shadows/highlights.

Mechanics for the kept files:
- Each one gets a header naming the upstream commit, both copyright holders, and what proof changed.
- Both full MIT texts go in a licences file next to the pipeline code (and in a `NOTICE`/third-party section of the README).

`spike/` vendors the unmodified upstream for testing only. It's never served by the app and gets deleted at the end of Phase 1.

## 2026-10-02 — Phase 1 closed: narrow mini-gl fork, filters from darktable, desktop + Android targets

The human confirmed three things:
- the **narrow fork** from the provenance audit above;
- that pipeline **filters will be borrowed from darktable**;
- that **Safari, iOS, and iPadOS are out of scope for v1**.

v1 targets current Firefox and Chromium-based browsers on desktop and Android. All three spike environments passed, and phones are supported but secondary.

**darktable as the filter source.** darktable is GPL-3.0-or-later, the same licence as proof, so its code can be ported directly. Each file header carries "Copyright (C) <years> darktable developers" and the source path at a pinned commit. The consequence is that proof can never be relicensed to a permissive licence without first removing that code. Its OpenCL kernels (`data/kernels/*.cl`) are the most direct source for GLSL. The two differences that matter: darktable's working space is linear Rec.2020, so primaries-dependent constants need converting, and multi-scale modules become multi-pass ops. Starting points to check when building each op in Phases 8–10, using darktable's `src/iop/` modules and kernels:

| proof tool (Snapseed name) | darktable starting point |
|---|---|
| Brightness / exposure | `exposure.c` |
| Contrast, saturation, vibrance | `colorbalancergb.c` (contrast around a grey fulcrum; perceptual saturation/chroma) |
| Highlights / Shadows | `shadhi.c` (Gaussian or bilateral mask; `gaussian.cl`, `bilateral.cl`). `toneequal.c` is the more advanced option |
| Curves | `rgbcurve.c` / `rgbcurve.cl` |
| Structure (Details) | `bilat.c` "local contrast" (`locallaplacian.cl`, or bilateral grid) |
| Sharpening (Details) | `sharpen.c` / `sharpen.cl` |
| White balance / warmth | Linear-light channel gains, informed by `channelmixerrgb.c`'s chromatic adaptation |
| Vignette | `vignette.c` |
| Black & White, grain | `channelmixerrgb.c` gray mixing or `monochrome.c`; `grain.c` |
| Ambiance | No direct equivalent. Decide when building, probably a blend of local contrast and vibrance |

Snapseed sets the UX: which sliders exist, with −100…+100 ranges and a gentle response near zero (the spike found mini-gl's mapping too sensitive). darktable sets the math.

**Half-float is required, with no 8-bit fallback.** Every target browser exposed `EXT_color_buffer_float`. A browser without it gets an "unsupported browser" message.

**The raw results JSON wasn't kept** (at the human's request). Its numbers are recorded in the entries above.

## 2026-10-02 — Phase 2 scaffolding choices

- **The mini-gl seed is committed verbatim first and changed afterwards.** The four kept upstream files go into `frontend/src/pipeline/minigl/` byte-for-byte from commit `28238857`, with only a provenance header added. Phase 8's restructuring (into `gl.js`/`runner.js`, half-float) then shows up in history as reviewable diffs against the upstream code, not as an unexplained rewrite. Until then, `minigl.js` still imports mini-gl's `minigl_filters.js`, which was deliberately excluded, so nothing loads these files yet.
- **Third-party notices live in `frontend/src/pipeline/LICENSES.md`**, holding both MIT texts in full (mini-gl, and glfx.js, which mini-gl derives from) plus a darktable section. A short "Third-party code" section in the README points to it.
- **Dependencies:** the same three pre-approved jars and pinned versions as `shelf` and `larder` (Postgres JDBC 42.7.13, kotlinx-serialization core/json 1.11.0), fetched and sha1-verified by `backend/lib/fetch-deps.sh`, and never committed. VanJS 1.6.1 was checked byte-identical to upstream (`vanjs-org/van` `public/van-1.6.1.js`, sha1 `8847b4b6…`).
- **`TestMain.kt` was pulled forward from Phase 3**, so `backend/test.sh` works from the first commit (with 0 tests).
- **The UI palette is strictly neutral grey with one safelight-amber accent.** Photo-editing UIs keep the chrome colourless, because a tinted surround biases how colour in the photo is judged. So, unlike the siblings' tinted palettes, every grey has equal R, G, and B. The accent is never placed behind a photo. Dark is the default, and light mode is supported, as in the siblings.

## 2026-10-02 — Phase 3 backend skeleton choices

- **Router, ApiResult, health, the static handler, and path safety are copied from `shelf`**, with the package renamed and only shelf-specific comments changed. The path-safety module was pulled forward from Phase 5, because serving `frontend/` already resolves client-supplied paths.
- **`resolveUserPath` is renamed to `resolveUnderRoot`.** proof resolves paths against the frontend directory, a user's data directory, and project directories, not only a user's home. The algorithm and its tests are unchanged.
- **Handler-pool threads are daemons.** `HttpServer.stop()` doesn't shut down a custom executor, so non-daemon pool threads kept the JVM alive after the end-to-end HTTP tests finished (`test.sh` hung after reporting 20/20). The JDK's `HttpServer` dispatcher thread is non-daemon and already keeps a running server alive, so daemon handler threads change nothing in production.
- **`main()` is split into `buildRouter()` and `createServer()`**, so the HTTP tests exercise exactly the router the app builds, on an ephemeral port.

## 2026-10-02 — Auth: shelf-style accounts (Phase 4)

This resolves brief §5. The human chose **`shelf`-style accounts** over no-auth (`press`'s model) or a single shared password. Personal photos are private, and separate accounts keep room for several household members. What was carried over and what changed:

- **Copied from `shelf` with packages renamed:** `ConnectionPool`, `Database`, `MigrationRunner`, `SessionRepository`, `PasswordHasher` (PBKDF2-HMAC-SHA256, 600k iterations), the cookie helpers, and the login, logout, and me handlers.
- **Dropped:** `shelf`'s device tokens. The Bearer-token path existed for shelf's Android app, and proof is browser-only, so `requireAuth` resolves the session cookie and nothing else. Also dropped are the unused `email`, `is_admin`, and `quota_bytes` columns.
- **The session cookie is `proof_session`:** HttpOnly, SameSite=Lax, and Secure when `PROOF_SECURE_COOKIES=true`. Sessions last 30 days by default.
- **Each user's directory is `$PROOF_DATA/<username>/`.** It's named by username, for the same reason as in shelf: the tree stays readable from outside the app. Usernames follow shelf's safe-segment rule **plus no leading dot**, because `$PROOF_DATA/.cache/` (thumbnails and previews) lives alongside user directories, and a user named `.cache` would collide with it.
- **Registration is open,** as in shelf. Anyone who can reach the app can create an account. Restricting it (an env flag, or invite-only) is a possible later change, not v1 scope.
- **The `projects` and `photos` tables moved from Phase 4 to Phase 5,** so each table lands with the code that first writes it. In particular, the EXIF columns get decided together with the EXIF reader.
- **The DB-backed flow was verified by hand against `postgres:18.6-alpine`:**
  - registration: 200, then 409 for a duplicate and 400 for a short password;
  - `/api/me` with a cookie: 200;
  - logout, then `/api/me`: 401;
  - a wrong password and an unknown user: an identical 401;
  - login, then `/api/me`: 200;
  - restart: no migration re-applied, and the account still logs in.

  The automated suite deliberately stays DB-free, as in shelf. The HTTP tests use a fake connection that fails on any access, which also proves the 401 and validation paths answer without a query.

## 2026-10-02 — Phase 5: projects, upload, ingest

- **Max upload is 100 MB** (`PROOF_MAX_UPLOAD_BYTES`), and **XMP sidecars are named `IMG_0001.jpg.xmp`** (darktable-style). The human decided both. This resolves those two brief §5 items.
- **ImageIO already colour-manages JPEGs.** A probe confirmed that a JPEG with an embedded ICC profile (linear RGB in the test) decodes to correctly converted sRGB: 0x80 linear became 0xBC. So P3 phone photos thumbnail with correct colour and no extra code. PNG `iCCP` handling wasn't checked, and PNGs are rare as camera output.
- **Re-uploading the identical file is idempotent.** The same filename with the same SHA-256 returns the existing photo with a 200, so a retried batch doesn't fail on files that already made it. The same name with different content is a 409. proof never silently overwrites an original.
- **Renditions are generated eagerly in the background and lazily on request.** After an upload, a 2-thread pool pre-generates the thumbnail and preview. A request for a missing one generates it inline. Both paths share one generation per photo, and a 2-slot semaphore bounds concurrent full decodes, at roughly 100+ MB of heap each for 24 MP. Rendition URLs carry the file's mtime as `?v=` and are served `immutable`.
- **Decode with subsampling, orient after scaling.** ImageIO source subsampling keeps at least 2x the 2048 px preview, which cuts decode heap and time for large files. Orientation is applied to the downscaled image, so a 2048 px image is rotated instead of a 24 MP one.
- **Capture time is stored as `TIMESTAMP` (no zone).** EXIF `DateTimeOriginal` is the camera's wall clock. `OffsetTimeOriginal` is kept in a separate column when present, rather than guessing a zone.
- **Project and photo names are portable path segments.** That means no `/ \\ : * ? " < > |` or control characters, no leading dot, no leading or trailing whitespace, and no trailing dot, so the tree stays usable over SMB/Windows. On top of that, they still go through `resolveUnderRoot`.
- **Bug caught by the smoke test, now fixed: renaming onto an empty project's name destroyed it.** `Files.move(..., ATOMIC_MOVE)` is `rename(2)` on Linux, which silently *replaces* an empty target directory. Renaming project A to the name of an existing, empty project B replaced B's directory with A's. The database update then failed with a unique violation, so the rollback moved A back, leaving B as a row with no directory. `fs/renameDirectory` now refuses whenever the target exists, and there's a regression test for it. A tiny race remains between the existence check and the move, and is accepted for a single-user-at-a-time app.
- **The upload queue shows per-file errors inline instead of a toast per failure.** A bad batch would otherwise stack dozens of toasts.
- **The project list loads before it's shown,** so going back from a project never flashes stale photo counts. That was found in the headless-Chrome run.

## 2026-10-02 — Phase 6 (reconciliation) deferred

The human chose to skip reconciliation for now. While it's deferred, everything that enters or changes proof's tree goes through the app, and the index can't notice changes made on disk outside it. Concretely:
- files copied into `originals/` over SMB don't appear;
- a project folder renamed outside the app makes its photos unreachable (404) until it's renamed back;
- XMP edits made by darktable aren't read back.

Missing thumbnails and previews already regenerate on demand, so the derived cache doesn't depend on reconciliation. The data stays files-as-truth regardless: originals and the sidecars proof writes are always on disk, so reconciliation can rebuild or repair the index whenever it lands.

## 2026-10-02 — Phase 7: culling and XMP sidecars

- **proof merges into sidecars and never overwrites them.** darktable keeps its *whole edit history* in the same `IMG_0001.jpg.xmp` file proof uses (the darktable-style naming chosen in Phase 5). Writing a fresh sidecar would destroy it. So `Xmp.write` parses the existing document, changes only proof's properties, and writes everything else back. A sidecar that doesn't parse gets a 409 `SIDECAR_UNREADABLE`, and proof won't touch it.
- **XMP mapping.** Standard XMP has stars (`xmp:Rating`) and a label (`xmp:Label`) but no pick flag:
  - **Reject** is written as `xmp:Rating="-1"`, the value Lightroom and darktable treat as rejected.
  - **Stars** are kept in `proof:Rating`, so un-rejecting restores them.
  - **The flag itself** goes in `proof:Flag`.
  - **The namespace** is `urn:x-proof:xmp:1.0`. The `x-` marks it unregistered, and proof doesn't claim a URL it doesn't own.
  - **Fallback:** a sidecar from another tool with no `proof:` fields falls back to the standard fields, with -1 meaning a reject.
- **Colour labels use Lightroom's `xmp:Label` names** (Red, Yellow, Green, Blue, Purple), on keys 6–9 as in Lightroom. darktable's own `darktable:colorlabels` isn't written.
- **Bug found by the smoke test, now fixed: sidecars grew on every write.** The serializer's `INDENT` re-indented on top of existing whitespace text nodes, so each rating change added blank lines, darktable's file included. Now only sidecars proof creates are indented. Existing ones are written back as they are, with a hand-written XML declaration and a normalised trailing newline, so repeated writes are byte-identical. Regression tests cover this, and 31 live writes (bursts of 3 concurrent) left a darktable sidecar clean.
- **The serializer orders attributes alphabetically.** It's semantically identical XML. darktable reads XMP through exiv2, which doesn't depend on attribute order.
- **Per-photo locking.** A sidecar update is read-modify-write, and rapid keypresses send overlapping PATCHes. They're serialized per photo using 64 striped monitors, so the lock table doesn't grow with photo count.
- **A PATCH returns the recounted view totals.** The UI updates its tab counts from that response instead of counting locally (the dumb-UI rule). Updates are optimistic for the photo the user just changed, since that only echoes their own keypress, and are then replaced by the server's version.
- **Culling doesn't reflow the sheet.** Rejecting a photo while viewing "Picks" doesn't remove it until the view is reloaded, matching Lightroom and Photo Mechanic. That way the selection doesn't jump while culling quickly.
- **No re-render flicker.** Each photo has its own reactive state, and frames read their static fields through VanJS `rawVal`, so a cull keypress re-renders a few badge nodes instead of re-creating every `<img>`.
- **Without Phase 6, an existing sidecar's rating isn't shown until proof writes to it.** A darktable rating of 1 shows as unrated in the grid. The first proof change to that photo reads the sidecar as its base, so nothing is lost, and the index then matches.

## 2026-10-02 — Phase 8: the edit pipeline core, ported from darktable

**Engine.** The verbatim mini-gl seed was split into `gl.js` (context, textures, programs) and `runner.js` (a stack runner with a texture pool), using `git mv` so history shows the derivation:
- **Half-float required:** intermediates are RGBA16F, with no 8-bit fallback.
- **Pooled resources:** ops get a `PassContext` and never allocate GL resources.
- **One output pass** feeds both the screen and the readback, so what's shown is what Phase 11 will save. It clamps NaN and out-of-range values and encodes sRGB.
- **Dither:** the output pass adds a deterministic dither under half a code value. It breaks up 16-to-8-bit banding but can't move an exactly representable value, so an untouched photo stays bit-identical (tested).

**darktable is the source for the filters.** Code was read at pinned commit `3fc4cfb2`, and every port keeps darktable's GPL notice:

| proof tool | darktable source | proof's deliberate differences (display-referred JPEG input, 0..1, vs darktable's unbounded scene-linear) |
|---|---|---|
| Brightness | colorbalancergb luminance power, `Y^(1/(1+p))` in Filmlight Yrg | white fulcrum = sRGB white |
| Contrast | colorbalancergb grey-fulcrum power (fulcrum 0.1845) | mirrored above the fulcrum, so 0→0 and 1→1 (darktable's pushes white past 1) |
| Saturation | colorbalancergb chroma in Ych, plus the Yrg gamut check | none |
| Ambiance | (none in darktable; Snapseed's isn't published) | proof's own: colorbalancergb vibrance plus a gentle shadow lift and highlight compression through shadhi |
| Shadows / Highlights | shadhi (Gaussian mode): blurred inverted L mask and the `overlay()` blend, ported from the OpenCL kernel | bounded mode (L clamped); shadows colour correction 50 % instead of 100 % (see below); mask sigma = 2.5 % of the long edge |
| Warmth, White Balance | CAT16 matrices from colorspace.h; illuminant from the CIE daylight locus (CIE 15) | relative to D65, so zero is exactly the identity; ±80 mired, ±0.02 duv |
| Curves | curve_tools.c monotone Hermite (no overshoot), flat beyond the end points | applied per channel in sRGB-encoded space (how curve editors are read); master then channel, baked into one LUT |
| Sharpening | sharpen.c: unsharp mask on Lab L, sigma = radius/2.5, soft threshold 0.5 | radius 0.06 % of the long edge (darktable scales its 2 px by the pipe scale too) |
| Structure | (darktable's bilat.c uses a local Laplacian pyramid: too many passes for interactive WebGL, especially on phones) | proof's own: a fast guided filter on Lab L (He et al.), the edge-aware primitive darktable's tone equalizer uses. It doesn't halo at strong edges (tested). |

**Colour-space notes.**
- **Working space:** proof works in linear sRGB (Rec.709), not darktable's Rec.2020. Every port goes through XYZ D65.
- **White point:** recomputed for proof's matrices. Its rg (0.21904, 0.54368) matches darktable's own (0.21902, 0.54371), which validates the port. The Kirk/CIE 2006 luminance of sRGB white is 1.058, not 1, so tone curves work on Y/1.058 and white maps exactly to white.

**Slider response.** Recipes store slider units (−100…100). Every slider is shaped by |v|^1.5 before mapping to darktable's ranges. The Phase 1 spike found linear sliders too sensitive near zero, and recipes stay meaningful if the maths changes.

**Found while testing on a smooth synthetic gradient and fixed.**
- **Structure amplified the source JPEG's 1-level quantisation steps into stripes.** It now only amplifies detail above a noise floor (about 0.3 to 1.2 L*), and only where the neighbourhood is genuinely textured (local standard deviation about 0.6 to 2 L*, from the guided filter's own means). Measured on a dark gradient, rows with visible jumps went 51 → 8 (the original has 7).
- **Shadows colour correction at darktable's 100 %** scales chroma with the lightness ratio, so lifting near-black pixels multiplied the JPEG's colour noise into brown bands. proof uses 50 %, darktable's own highlights default, and the band is gone.

**Known limitation.** Lifting shadows hard on an 8-bit JPEG stretches its quantisation steps, and structure applied after a strong lift can still emphasise them a little. That's inherent to 8-bit sources, and Snapseed shows the same thing on skies. Real photos' sensor noise hides most of it. Debanding on decode is a possible later addition.

**Editor without saving.** Phase 8's editor works on the 2048 px preview and keeps the recipe in memory only. Saving the render and recipe is Phase 11. Until then, closing with edits asks for confirmation.

## 2026-10-02 — Phase 9: geometry tools

- **Perspective is keystone sliders (vertical, horizontal), not four draggable corners as planned.** Keystone is the common fix (converging verticals from tilting the camera), and dragging four corners precisely on a phone-sized preview is fiddly. Underneath, it's a general four-corner homography (mini-gl/glfx's square-to-quad, MIT), so a free-corner mode only needs a new parameter and a migration. The source quad is always *inside* the photo, so the output is fully covered and no fill colour or edge handling is needed. The cost is a slight stretch, as in Snapseed's tilt.
- **Straighten auto-crops.** The output is the largest rectangle with the image's own aspect that fits inside the rotated photo: `min(W / (W·cos + H·sin), H / (W·sin + H·cos))`. That means no blank corners, matching Snapseed and Lightroom. A test checks that no corner of the crop maps outside the photo for every angle in ±45° at several aspects, and that a 2 % larger crop would.
- **Crops, quarter turns, and flips are exact copies.** Rectangles are rounded to whole pixels, and every output pixel centre lands on an input pixel centre, so no resampling happens. Fine rotation and perspective use Catmull-Rom bicubic (16 taps), which is crisper than bilinear. Tests compare every pixel of turns and flips against a loop-based reference written from the definitions.
- **Geometry changes the working size, so each op's context is sized from its input.** Spatial tools after a crop work relative to the cropped image. That's still identical between preview and export, which is the property that matters.
- **The editor shows a crop step's input while it's selected** (the stack before it, plus a crop box), the way Snapseed and Lightroom present cropping. Rotate and Perspective show their live result with an alignment grid. A consequence of the stack model: while adjusting a crop, edits stacked *after* it aren't visible. They reappear on Done.
- **mini-gl's remaining seed files are gone.** `filterPerspective.js`'s homography helpers live on in `geometry.js` with their MIT notices. `filterMatrix.js` wasn't needed, because rotation is proof's own output-to-input mapping.

## 2026-10-02 — Phase 10: Vignette and Black & White

The human asked for the remaining phases to be done in one go, skipping Phase 12 (export).

- **Vignette** is darktable's `vignette.c`:
  - the "automatic ratio" super-ellipse, so the ellipse follows the frame;
  - an inner radius plus a fall-off;
  - darkening multiplicative, brightening additive.

  proof's differences:
  - the cosine ease is always on (darktable eases only when dithering), so there's no visible edge where the fall-off starts;
  - Snapseed's *inner* brightness is added, as the inverted weight;
  - darktable's saturation term isn't exposed.
- **Black & White** combines three darktable modules:
  - **Film response:** channelmixerrgb's monochrome presets. These are XYZ weights that darktable derived from the manufacturers' published spectral sensitivities, normalised so white stays white.
  - **Lens colour filters:** monochrome.c's Lab Gaussian filter, blurred so it follows areas, not JPEG chroma noise.
  - **Grain:** grain.c's 3-octave simplex noise with darktable's grain power spectrum and paper-response LUT.

  proof's differences:
  - **Colour filter:** it's divided by its own response to grey, so greys keep their tone and colours near the filter's hue get *lighter*. darktable's monochrome only ever darkens, and a real filter is used with exposure compensation.
  - **Grain seed:** it's the same for every photo. darktable seeds it from the filename, but a recipe has to render identically wherever it's reopened.
  - **Grain in previews:** it's averaged over 4 samples when the finest octave is under 4 px, as darktable does when zoomed out with its 21-sample lattice. So the downscaled preview shows what the export will look like at the same size.
- **Brightness and contrast are shared code.** Black & White's sliders use exactly Tune's curves (`TONE_FUNCTIONS`), so the two tools respond the same way.
- **A new parameter kind, `choice`, gets a generic button-row control** (`components/Choice.js`). Tools can opt out of the "identity at defaults" test with `identityAtDefaults: false`, as Black & White does: making a photo grey is the point of the tool.

## 2026-10-02 — Phase 11: saving, reopening, and reverting edits

- **One request carries the render and the recipe**, framed as `[4-byte big-endian recipe length][recipe JSON][JPEG]`. They must be written together, and a hand-rolled multipart parser is more code to get subtly wrong than a length prefix. The recipe is capped at 256 KB, and the render at the upload cap.
- **The server still treats the recipe as opaque.** It checks only that it's a JSON object with a *numeric* integer `version` (a string `"1"` is refused, caught by a test) and a `stack` array. It stores the text verbatim and returns it parsed on `GET`.
- **Optimistic concurrency.** The editor sends `?base=<editVersion>` (the saved edit's mtime in milliseconds, or `none`). The server refuses a save from a stale base with a 409, so a second tab can't silently overwrite a newer edit.
- **The editor always edits the original.** A new SOURCE rendition (a 2048 px preview of the original, `/api/photos/:id/source`) feeds the editor, while the display renditions switch to the render after a save. Saving fetches the original, decodes it upright with `createImageBitmap(..., {imageOrientation: "from-image"})`, renders the recipe at full resolution through the same pipeline as the preview, encodes JPEG 0.92 in the browser, and restores the preview source. Edits are never stacked on a previous render.
- **EXIF on renders.** The original's Exif APP1 is spliced in right after SOI with IFD0 Orientation reset to 1, in both byte orders, and any Exif already in the render is replaced. The ICC profile is not copied, because the render is sRGB. This follows the Phase 1 spike.
- **Render file names** follow the original: `IMG_0001.jpg` → `edits/IMG_0001.jpg`, and a PNG's render is `edits/<name>.png.jpg`. Saving is refused if two originals in a project would map to the same render file.
- **Bug found while verifying, now fixed: proof's files were owner-only (`rw-------`).** Every atomic write goes through `Files.createTempFile`, which creates `0600`, so originals, renders, recipes, and XMP sidecars ended up unreadable to other local users, the SMB daemon included. That defeats the files-as-truth design. They're now set to `rw-r--r--` once in place (`fs/makeShareable`), with a test.
- **Memory.** The full-resolution render reuses the editor's WebGL context. The preview's textures are dropped first, and the preview is re-uploaded afterwards, so only one context's worth of 16-bit textures is ever alive. A photo larger than the GPU's maximum texture size gets a clear error. Tiled rendering stays a v2 item.

## 2026-10-03 — Clickable culling in the loupe

The loupe showed a photo's rating, flag, and label but only the keyboard could change them. That left nothing to click, nothing on screen to say the keys work there, and no way to cull on a touch device. Its bar now has controls:
- Pick and Reject toggles;
- five stars, with a hover preview of the rating a click would set (pointer devices only, since `:hover` sticks after a tap). Clicking the current rating clears it, as `0` does;
- colour-label dots (Red, Yellow, Green, Blue, Purple; the first four also have keys 6–9).

**How they work:**
- They go through the same `cull()` as the keys, so the optimistic update, the PATCH, and the rollback on error are shared. The tab counts update the same way.
- Each button cancels `mousedown` so it never takes focus. Without that, Enter or Space would press the last-clicked button again, instead of the loupe's keys (Enter, arrows) doing their usual job.

**Layout:** on wide screens the bar stays one row, with the filename and EXIF truncating and the key hint shown. On phones it wraps into rows with larger star targets.

Checked with real mouse events in headless Chrome:
- each control changes the server's state;
- a second click on Pick or the current star clears it;
- Enter after a click changes nothing;
- focus stays on `body`, and the arrows and `3`/`P` keep working.

## 2026-10-03 — Swiping between photos in the loupe

On phones the loupe hid its ‹ › buttons and there's no keyboard, so there was no way to move to the next photo. A one-finger horizontal swipe now does it, and the photo follows the finger.

**How it works:**
- The loupe renders a three-slide strip: the previous, current, and next previews, the neighbours off-screen either side. This replaces the `<link rel="preload">` tags, which did the same preloading, and it means the incoming photo is visible while dragging.
- Letting go past a fifth of the width, or with a flick (above 0.4 px/ms and 30 px), animates the rest of the way and steps. Anything less springs back. Past the first or last photo the drag moves at a third of the finger's speed and never steps.
- The drag offset is written to the strip's style directly, not to van state, because it's per-frame presentation that nothing else reads. `prefers-reduced-motion` skips the animations.

**Gestures it doesn't take over:**
- **Touch and pen only.** A mouse drag does nothing, because desktop has the arrow keys and the buttons.
- **Vertical drags do nothing.** The stage's `touch-action: pinch-zoom` also stops the contact sheet behind from scrolling.
- **Pinch-zoom stays the browser's**, so you can still zoom in to check focus. While the page is zoomed (`visualViewport.scale > 1`), swipes are ignored and `touch-action` is relaxed, so one finger pans the zoomed view.
- **A tap beside the photo still closes the loupe.** A click that arrives within 400 ms of a swipe is ignored.

Checked with emulated touch at phone size in headless Chrome:
- swipes step both ways, and stop at both ends;
- a slow short drag springs back, and a fast short flick steps;
- vertical drags, mouse drags, and swipes while zoomed are ignored, and swipes work again after zooming out;
- rating then swiping saves the rating to the right photo;
- a tap above the photo closes the loupe.

The desktop arrow keys and buttons are unchanged.
