# Decisions log

An append-only record of decisions made while building proof, beyond what `PROJECT_BRIEF.md` and `V1_PLAN.md` already fix. The newest entries are at the bottom. Don't relitigate any of these without flagging it to the human first.

## 2026-10-02 — App name: proof

Named after the proof sheet (contact sheet), which is what culling is done on. It pairs with `press`. Other candidates considered: easel (rejected as "too painterly"), mantel, tray, plate, and contact.

## 2026-10-02 — Edits render entirely in the browser (WebGL2)

Three options were weighed for where the edit pipeline runs:

1. **Kotlin renders everything.** The server renders a debounced preview from a cached working copy, and renders the export. There's one implementation, and the UI stays fully dumb. But every slider movement costs a network round-trip plus a JPEG encode, so it would never feel like Snapseed.
2. **A WebGL preview plus a Kotlin export.** This feels instant, but every tool gets written twice, in GLSL and in Kotlin, and the two drift apart. The result is that what you see isn't what gets saved.
3. **The browser renders everything.** There's one implementation, in the place where it has to be fast anyway.

The human chose option 3, with one refinement: the browser sends the finished render back to the API, and the server stores it. A photo that's mid-edit is ephemeral working state. Once it's saved, the server holds the truth, which is just generated by the browser. Consequences:
- The server never runs an edit pipeline.
- Thumbnails and exports come from the stored render.
- The "API is source of truth / dumb UI" rule from `larder` gets one narrow, recorded exception for pixels (see the next entry).

## 2026-10-02 — Narrow exception to the dumb-UI rule: the pixel pipeline

The standing rule (filtering, formatting, and derived values belong in the API) still holds for everything in proof except pixels. The WebGL pipeline lives only in `frontend/src/pipeline/` and never touches project, rating, or list state. Cull views, counts, and display strings all come from the API. See `AGENTS.md`.

## 2026-10-02 — Store the render *and* an opaque recipe

Saving an edit stores two files: the full-resolution rendered JPEG and a JSON recipe (the edit stack with its schema version). The server validates the recipe only as JSON within a size cap and never interprets it. It hands the recipe back unchanged so the browser can reopen the stack and keep editing non-destructively, like Snapseed's "View edits". The alternative, storing the render only, was rejected because it would make re-editing start over from the original, for the sake of saving a few KB per photo. Recipe schema migrations are entirely the frontend's job.

## 2026-10-02 — Files are the truth, with a Postgres index (`shelf`'s model)

Photos have an obvious natural file form, and users may want to reach them from outside the app (SMB, darktable). So originals, renders, recipes, and XMP rating sidecars are real files, and Postgres is a rebuildable index over them, with `shelf`'s reconciliation machinery reused. The alternatives were:
- **Postgres as the source of truth** (`larder`'s model), rejected because it locks cull and edit work inside the app;
- **files with no database** (`press`'s model), rejected because cull views need fast filter, sort, and count queries over hundreds of photos per project.

## 2026-10-02 — v1 input formats: JPEG and PNG only

`javax.imageio` handles both with no new dependency. EXIF reading and the EXIF re-attach on save are hand-written, needing only a small TIFF IFD parser and a byte-level APP1 segment splice. HEIC and camera RAW are deferred to v1.5. They'd most likely use apt-packaged CLI decoders run through array-args `ProcessBuilder` (`press`'s pattern), proposed as a dependency at that time.

## 2026-10-02 — Single-shot per-file uploads, not chunked

Photos are 5–20 MB each, so a client-side queue of about 3 concurrent single-file `POST`s, each streamed to disk, is enough. This is `press`'s reasoning. `shelf`'s chunked/resumable machinery is for multi-gigabyte, possibly multi-day transfers, which this app doesn't have.

## 2026-10-02 — WebGL2 spike comes first

The browser pipeline is the one genuinely novel risk in the project, in the same way the printer driver was for `press`. `V1_PLAN.md` Phase 1 is a throwaway spike that measures, on the real target devices: 24 MP texture load, interactive frame rate with a stacked pipeline, half-float support and banding, full-resolution export time, colour fidelity, and the EXIF splice. Its findings, with numbers, get recorded here before any repo code is written.
